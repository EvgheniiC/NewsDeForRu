# TODO: поиск официального первоисточника по сигналам крупных СМИ

Состояние на 12.08.2026.

> Цель: использовать ZEIT, WELT, SPIEGEL и ZDF heute только как сигналы о
> событии. Публикуемый материал должен создаваться по официальному
> первоисточнику: полиции, прокуратуре, пожарной службе, суду, городу или
> другому государственному органу.
>
> На этапе тестирования все созданные материалы без исключений направляются в
> раздел модерации. Автопубликация, Telegram и push до решения модератора
> запрещены.
>
> Это технический план, а не юридическая консультация. До подключения RSS или
> автоматизированного доступа необходимо проверить условия использования
> каждого канала обнаружения.

---

## 1. Основной принцип

Новый pipeline не должен переводить или переписывать статьи крупных СМИ.

Допустимый поток:

1. ZEIT, WELT, SPIEGEL или ZDF heute сообщает о событии.
2. Система извлекает только признаки события: место, примерное время, тип
   происшествия и упомянутое ведомство.
3. По этим признакам система ищет официальный пресс-релиз.
4. События сопоставляются по нескольким признакам.
5. LLM получает официальный материал, а не текст статьи СМИ.
6. Создаётся самостоятельный русскоязычный черновик.
7. Черновик всегда попадает в модерацию.
8. Публикация возможна только после ручного подтверждения.

Недопустимый поток:

- скачивание полного текста статьи и близкий рерайт;
- обход paywall, авторизации, CAPTCHA или технических ограничений;
- перевод статьи абзац за абзацем;
- копирование заголовка, фотографий, видео, инфографики и длинных цитат;
- публикация без найденного и проверенного официального источника;
- автоматическое дополнение отсутствующих фактов моделью.

## 2. Границы первой версии

### Источники-сигналы

- `die_zeit` — ZEIT;
- `welt` — WELT;
- `spiegel` — SPIEGEL;
- `zdf` — ZDF heute.

### Поддерживаемые события

- убийство или подозрение на убийство;
- ножевая атака;
- стрельба;
- взрыв;
- драка или массовая потасовка;
- наезд автомобиля на людей;
- нападение;
- крупная операция полиции;
- происшествие с несколькими пострадавшими.

### Официальные первоисточники

Приоритет поиска:

1. полиция федеральной земли или города;
2. Bundespolizei;
3. прокуратура;
4. пожарная служба и спасательные службы;
5. суд;
6. официальный портал города или федеральной земли;
7. федеральное ведомство.

Информационные агентства и другие СМИ не считаются официальным
первоисточником для автоматической публикации.

## 3. Целевая архитектура

```text
Publisher RSS / разрешённый discovery-канал
                    |
                    v
             DiscoverySignal
                    |
                    v
        Event extraction and classification
                    |
                    v
          Official source candidate search
                    |
                    v
       Candidate matching and verification
                    |
          +---------+---------+
          |                   |
          v                   v
    Official source found   Source not found
          |                   |
          v                   v
   Fetch official text    Moderation research task
          |
          v
   Independent editorial LLM
          |
          v
       Safety validation
          |
          v
     NEEDS_REVIEW only
```

## 4. Модели данных

### 4.1. `DiscoverySignal`

Сохраняет факт обнаружения события без превращения текста СМИ в публикацию.

Предлагаемые поля:

- `id`;
- `publisher_source_key`;
- `publisher_url`;
- `rss_guid`;
- `rss_title`;
- `rss_summary`;
- `published_at`;
- `retrieved_at`;
- `event_type`;
- `event_city`;
- `event_state`;
- `event_time_from`;
- `event_time_to`;
- `mentioned_authority`;
- `event_fingerprint`;
- `processing_status`;
- `created_at`.

RSS-заголовок и summary используются только внутри discovery-процесса. Они не
должны попадать в публичный API и пользовательскую ленту.

### 4.2. `OfficialSourceCandidate`

- `id`;
- `discovery_signal_id`;
- `authority_name`;
- `official_url`;
- `official_domain`;
- `title`;
- `published_at`;
- `location`;
- `match_score`;
- `match_reasons_json`;
- `is_selected`;
- `retrieved_at`.

### 4.3. `VerificationBundle`

- ссылка на выбранный сигнал;
- ссылка на официальный материал;
- совпавшие признаки;
- противоречия;
- отсутствующие данные;
- итоговый уровень уверенности;
- версия правил проверки.

### 4.4. Статусы

Предлагаемые внутренние статусы:

- `discovered`;
- `extracting`;
- `searching_official_source`;
- `needs_source_review`;
- `official_source_found`;
- `verified`;
- `rejected`;
- `expired`.

Публичный `ProcessedNews` создаётся только после нахождения официального
источника. На тестировании его `publication_status` всегда равен
`NEEDS_REVIEW`.

## 5. Этапы реализации

### Этап 0. Правила доступа и конфигурация

- [ ] Проверить условия использования RSS ZEIT, WELT, SPIEGEL и ZDF heute.
- [ ] Не загружать HTML статьи, если для discovery достаточно RSS.
- [ ] Не открывать paywall программно.
- [ ] Добавить отдельный список `DISCOVERY_SOURCE_KEYS`.
- [ ] Не смешивать его с `RSS_ENABLED_SOURCE_KEYS`, который разрешает
      публикационный ingestion.
- [ ] Добавить `DISCOVERY_PIPELINE_ENABLED=false` по умолчанию.
- [ ] Добавить `DISCOVERY_FORCE_MODERATION=true`, без возможности отключения в
      тестовом окружении.
- [ ] Ограничить объём и частоту запросов.
- [ ] Соблюдать robots.txt и условия конкретных официальных сайтов.

Результат: discovery-канал технически отделён от источников публикуемого
контента.

### Этап 1. Ingestion сигналов

- [ ] Создать `PublisherDiscoveryIngestionService`.
- [ ] Получать только разрешённые RSS-поля.
- [ ] Удалять HTML-разметку и tracking-параметры.
- [ ] Не сохранять изображения издателя.
- [ ] Исключать повторные сигналы по `guid` и URL fingerprint.
- [ ] Ввести TTL: старые сигналы не обрабатывать.
- [ ] Ограничить количество сигналов за один запуск.
- [ ] Логировать источник и fingerprint без полного текста.

Результат: событие обнаруживается, но статья не поступает в текущий
публикационный pipeline.

### Этап 2. Извлечение признаков события

- [ ] Создать типизированную Pydantic-схему `EventExtraction`.
- [ ] Извлекать город, федеральную землю, время, тип события и ведомство.
- [ ] Поддержать немецкие варианты географических названий.
- [ ] Нормализовать время в `Europe/Berlin`.
- [ ] Не выводить мотив, гражданство и другие чувствительные признаки.
- [ ] Для неопределённых значений возвращать `None`, а не догадку.
- [ ] Добавить confidence по каждому извлечённому полю.
- [ ] Формировать стабильный `event_fingerprint`.

Минимальный fingerprint:

```text
event_type + normalized_city + event_date + approximate_time_bucket
```

Результат: структурированный поисковый запрос без копирования редакционного
текста.

### Этап 3. Реестр официальных источников

- [ ] Создать `OfficialAuthorityRegistry`.
- [ ] Добавить федеральные домены.
- [ ] Добавить полицию и прокуратуру всех 16 федеральных земель.
- [ ] Добавить Bundespolizei.
- [ ] Добавить основные городские пожарные службы.
- [ ] Для каждого источника хранить тип доступа: RSS, API, HTML search или
      внешний search API.
- [ ] Хранить allowlist официальных доменов.
- [ ] Запрещать выбор кандидата с домена вне allowlist.

Начать с пилотных регионов:

- [ ] Bremen;
- [ ] Berlin;
- [ ] Hamburg;
- [ ] Nordrhein-Westfalen;
- [ ] Bayern.

После стабилизации расширить на всю Германию.

### Этап 4. Поиск официального сообщения

- [ ] Сначала искать в RSS/API соответствующего ведомства.
- [ ] Затем использовать поиск на официальном сайте.
- [ ] В крайнем случае использовать поисковый API с ограничением по
      официальным доменам.
- [ ] Строить запрос из города, даты, типа события и ключевых слов.
- [ ] Искать публикации в окне от 12 часов до события до 72 часов после него.
- [ ] Поддержать обновлённые пресс-релизы и совместные сообщения полиции и
      прокуратуры.
- [ ] Кэшировать результаты поиска.
- [ ] Ограничить количество кандидатов.

Если кандидат не найден:

- [ ] создать задачу `needs_source_review`;
- [ ] показать модератору ссылку на сигнал СМИ и поисковые параметры;
- [ ] не создавать готовую новость;
- [ ] не запускать редакционный LLM.

### Этап 5. Сопоставление событий

Один общий термин вроде `Messerangriff` недостаточен.

Минимальные признаки совпадения:

- город или район;
- дата и допустимое временное окно;
- тип события;
- количество участников или пострадавших, если известно;
- место: вокзал, улица, школа, мероприятие;
- упомянутое ведомство.

- [ ] Реализовать детерминированный score до применения LLM.
- [ ] Использовать LLM только для объяснения неоднозначных совпадений.
- [ ] Установить высокий порог автоматического выбора кандидата.
- [ ] При противоречиях всегда отправлять на ручной поиск.
- [ ] Сохранять причины совпадения для аудита.
- [ ] Не объединять разные происшествия только из-за одного города и типа.

Результат: у каждого материала есть проверяемая связь с официальной
публикацией.

### Этап 6. Загрузка официального материала

- [ ] Загружать только выбранный официальный URL.
- [ ] Проверять redirect и конечный домен по allowlist.
- [ ] Ограничить размер ответа и timeout.
- [ ] Удалять навигацию, cookie-banner и посторонний контент.
- [ ] Не загружать фотографии без отдельного разрешения.
- [ ] Сохранять дату получения и хеш нормализованного текста.
- [ ] Обнаруживать последующие изменения официального сообщения.
- [ ] Хранить ссылку и необходимые доказательства происхождения.

### Этап 7. Редакционный LLM

- [ ] Передавать модели текст официального сообщения и metadata события.
- [ ] Не передавать полный текст статьи ZEIT/WELT/SPIEGEL/ZDF.
- [ ] Создавать самостоятельный русский текст.
- [ ] Требовать атрибуцию: «По данным полиции…».
- [ ] Сохранять статус утверждений: подтверждено, предварительно, неизвестно.
- [ ] Запретить предположения о мотиве, происхождении, религии, здоровье и
      терроризме.
- [ ] Использовать «подозреваемый», а не «преступник».
- [ ] Запретить кликбейт и графические подробности.
- [ ] Не публиковать персональные данные без отдельного основания.
- [ ] Снижать confidence при неполных или противоречивых данных.
- [ ] Возвращать типизированный JSON.

### Этап 8. Проверки после LLM

- [ ] Проверить, что официальный URL присутствует.
- [ ] Проверить, что домен находится в allowlist.
- [ ] Проверить фактические числа, даты, имена ведомств и географию.
- [ ] Проверить отсутствие длинных совпадений с discovery RSS.
- [ ] Проверить запрещённые чувствительные формулировки.
- [ ] Проверить презумпцию невиновности.
- [ ] При любой ошибке отправлять материал в модерацию с причиной.
- [ ] Никогда не заменять ошибку LLM автоматически опубликованной заглушкой.

### Этап 9. Обязательная модерация

- [ ] Для всех материалов нового pipeline устанавливать `NEEDS_REVIEW`.
- [ ] Добавить причину `OFFICIAL_SOURCE_PIPELINE_TESTING`.
- [ ] Не учитывать высокий `confidence_score` как основание для публикации.
- [ ] Не отправлять Telegram и push до ручного approve.
- [ ] Показывать модератору:
  - сигнал СМИ;
  - официальный источник;
  - совпавшие признаки;
  - противоречия;
  - текст черновика;
  - дату получения обоих источников.
- [ ] Добавить действия:
  - подтвердить источник;
  - выбрать другого кандидата;
  - отредактировать материал;
  - отклонить;
  - отложить до появления официального сообщения.

### Этап 10. Обновления новости

- [ ] Повторно проверять официальный источник через заданные интервалы.
- [ ] Обнаруживать исправления числа пострадавших и процессуального статуса.
- [ ] Не перезаписывать опубликованный текст без аудита.
- [ ] Создавать новую версию материала.
- [ ] Все обновления во время тестирования также отправлять в модерацию.

### Этап 11. Наблюдаемость

- [ ] Метрики количества discovery-сигналов.
- [ ] Доля найденных официальных источников.
- [ ] Доля ложных совпадений.
- [ ] Среднее время поиска.
- [ ] Расход LLM и search API на один подтверждённый материал.
- [ ] Количество материалов, отклонённых модератором.
- [ ] Причины отклонения.
- [ ] Алерт при неожиданной автопубликации из нового pipeline.

## 9. Сложность и сроки

Общая сложность: **выше средней, примерно 7 из 10**.

Самая сложная часть — не LLM-промпт, а надёжный поиск и сопоставление
официального сообщения с событием. Официальные сайты имеют разные форматы,
поиск и скорость публикации. Иногда официальный релиз появляется позже СМИ
или не появляется вообще.

### Оценка для одного разработчика

#### Минимальный пилот: Bremen + один discovery-источник

- проектирование и модели БД: 2–3 дня;
- ingestion и event extraction: 2–3 дня;
- реестр и поиск официальных сообщений: 3–5 дней;
- matching и verification: 3–4 дня;
- LLM и safety validation: 2–3 дня;
- moderation UI/API: 2–3 дня;
- тесты и стабилизация: 3–5 дней.

Итого: **17–26 рабочих дней**, приблизительно 4–6 недель для одного
разработчика с учётом исправлений и ручной проверки.

#### Production-ready Германия

Реалистичная оценка: **8–14 недель** для одного опытного разработчика.

При участии двух разработчиков и редактора/тестировщика календарный срок можно
сократить примерно до **5–9 недель**, но объём работы не уменьшается
пропорционально.

### Что можно сделать быстрее

Упрощённый MVP без новой moderation UI и только для Bremen:

- использовать существующую очередь модерации;
- искать только Polizei Bremen;
- не обрабатывать обновления;
- не использовать общий web search;
- при отсутствии точного совпадения сразу создавать research task.

Такой вариант возможен примерно за **8–12 рабочих дней**, но он не готов для
всей Германии.

---

## 10. Денежные затраты

Ниже приведены ориентиры, а не коммерческое предложение.

### Если разработка выполняется самостоятельно

Прямые расходы пилота:

- LLM API: ориентировочно 10–100 евро в месяц;
- search API, если потребуется: 0–150 евро в месяц;
- дополнительная инфраструктура и мониторинг: 10–100 евро в месяц;
- юридическая проверка: ориентировочно 500–2 500 евро однократно.

Итого для небольшого теста: примерно **20–350 евро в месяц** без учёта
собственного времени и юридической консультации.

### Если нанимать разработчика

При ставке 400–800 евро за рабочий день:

- упрощённый MVP: примерно 3 200–9 600 евро;
- пилот 4–6 недель: примерно 6 800–20 800 евро;
- production-ready Германия: ориентировочно 16 000–56 000 евро.

Разброс большой, потому что стоимость зависит от числа поддерживаемых
официальных сайтов, качества их API/RSS и требуемой точности matching.

### Основные постоянные затраты

- LLM-вызовы;
- поисковый API;
- хранение и мониторинг;
- работа модератора;
- поддержка адаптеров при изменениях официальных сайтов;
- периодическая юридическая проверка.

При небольшом потоке новостей главным расходом будет не LLM, а человеческая
модерация и сопровождение интеграций.

## 11. Риски

- условия RSS могут запрещать автоматизированное коммерческое использование;
- официальный источник может отсутствовать или появиться с задержкой;
- разные происшествия могут иметь одинаковые признаки;
- первоначальные данные полиции могут измениться;
- LLM может добавить правдоподобный, но неподтверждённый факт;
- официальный сайт может изменить HTML или структуру URL;
- обработка персональных данных требует отдельной осторожности;
- высокая срочность не должна обходить модерацию;
- ссылка СМИ не доказывает совпадение с найденным официальным сообщением.

## 12. Definition of Done для пилота

- [ ] ZEIT/WELT/SPIEGEL/ZDF используются только как discovery-сигналы.
- [ ] Полный текст статьи СМИ не загружается и не передаётся LLM.
- [ ] Итоговый текст строится по официальному источнику.
- [ ] Официальный URL и доказательства matching сохранены.
- [ ] При отсутствии источника публикационный текст не создаётся.
- [ ] Все материалы и обновления попадают в модерацию.
- [ ] Автопубликация, Telegram и push до approve невозможны.
- [ ] Есть аудит действий модератора.
- [ ] Есть автоматические тесты и offline-набор исторических событий.
- [ ] Пилот достигает установленных критериев точности.
